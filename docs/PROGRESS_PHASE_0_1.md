# Headroom Monitor — Progress report, Phases 0 and 1

Period: 29–30 September 2026 · Author: Daniele · Status: **Phases 0 and 1 complete**

Headroom Monitor is a 13-week cash-forecasting and liquidity early-warning module, designed as an
extension of Financial Navigator by A352 for the LHoFT Best Case Study Competition 2026.
This report records what was built in the first two phases, the decisions taken, the problems found
and how they were fixed.

---

## 1. Where we are, in one paragraph

The project now has a clean, isolated code base (Phase 0) and a complete **data foundation**
(Phase 1): a protected PostgreSQL database with role separation, encryption and audit logging;
official public data from STATEC and the ECB; and a reproducible generator that creates a fictional
Luxembourg building-materials distributor with 237 customers, one year of history and 13 weeks of
hidden "future", in 8 scenarios. Each scenario hides a specific cash problem and ships with an
automatic check proving the problem is really there. Everything is committed and pushed to a
private GitHub repository. 101 automated tests pass.

## 3. Phase 1A — Database, roles, vault, audit

### What exists

- **4 schemas**: `hm` (operational data), `vault` (encrypted names), `eval` (hidden truth and future
  actuals), `audit` (change log).
- **19 tables in `hm`**: datasets, company parameters, bank accounts, balances and transactions,
  counterparties (codes only), customer invoices and receipts, supplier invoices and payments,
  recurring outflows, credit facilities, month closes and adjustments, versioned parameters,
  approvals, forecast runs and lines, public series.
- **9 migrations** (`migrations/001`–`009`), applied by `scripts/migrate.py`, idempotent and tracked
  in `hm.schema_migrations`.

### Roles (least privilege)

| Role | Can |
|---|---|
| `hm_reader` | Read `hm` |
| `hm_analyst` | Read + write forecasts + propose parameters. **This is the role the application uses** |
| `hm_approver` | Analyst + approve parameters and actions + read the audit log |
| `hm_evaluator` | Read `hm` and `eval` (only for measuring forecast error) |
| `hm_admin` | Everything, including the vault. Used only by the generator |

### Protection mechanisms

- **Vault**: display names and IBANs encrypted with `pgcrypto` (`pgp_sym_encrypt`); key in `.env`.
  Primary key `(dataset_id, code)`.
- **Audit log**: a database trigger on every `hm` table records who changed what, with old and new
  values. The trigger runs as `SECURITY DEFINER` with a fixed `search_path`, so every role is audited
  even without write access to the log.
- **Immutable records**: `hm.parameters` rejects UPDATE and DELETE (new versions only);
  no application role can modify or delete `audit.log`.
- **Hidden truth**: the application role cannot read `eval.*`, so the forecasting system cannot
  "cheat" by looking at the future.

### Security review — problems found and fixed

| # | Problem | Fix |
|---|---|---|
| 1 | Secrets printed in plain text and generated by an LLM (not truly random) | Regenerated with `secrets.token_urlsafe(32)`, never printed again |
| 2 | Any role could switch off row-level auditing via a session setting | Bulk mode allowed only for `hm_admin`, checked with `session_user` (migration 009) |
| 3 | Audit recorded the function owner instead of the real user | `session_user` instead of `current_user` inside the trigger |
| 4 | Approved parameters could be deleted | DELETE blocked by trigger |
| 5 | Vault could not distinguish scenarios | Composite key `(dataset_id, code)` |
| 6 | An already-applied migration file was edited | Reverted; all fixes go into new migration files |

## 4. Phase 1B — Public data

| Source | Series | Status |
|---|---|---|
| ECB Data Portal (live API) | Deposit facility rate `FM/B.U2.EUR.4F.KR.DFR.LEV` | 69 observations loaded |
| ECB Data Portal (live API) | 3-month Euribor `FM/M.U2.EUR.RT.MM.EURIBOR3MD_.HSTA` | 392 observations loaded |
| STATEC / LUSTAT | *Faillites prononcées par les tribunaux de commerce selon l'activité économique*, dataflow `LU1:DSD_DEMO_ENT_2@DF_D1312`, annual 2016–2025, all sectors, CC0 licence | 150 observations loaded from the official CSV |

**Decision — one source only.** Press releases and the LUSTAT table give different totals
(e.g. 2025: 1,187 vs 1,153; construction 2024: 197 vs 200), because they use different aggregates.
All press figures were removed; the LUSTAT table is the single source.

**LUSTAT API.** The SDMX API is not reachable from outside (the server returns the web page), so the
official table was downloaded by hand and committed to `data/public/raw/` with its source URL.
The code tries the API first and falls back to the file.

### Sector stress index

Formula: bankruptcies in 2025 / average 2020–2024. 1.0 = normal.

| Sector (customer segment) | 2025 | Average 2020–24 | Stress index |
|---|---|---|---|
| Construction (general contractors, installers) | 164 | 141.4 | **1.16** |
| Real estate (developers / renovation) | 61 | 37.8 | **1.61** |
| Retail trade | 81 | 82.2 | 0.99 |
| Wholesale trade (our own sector) | 87 | 90.0 | 0.97 |
| Total economy | 1,153 | 1,080.4 | 1.07 |
| Public entities | — | — | 1.00 (fixed; not in the table) |

Effect on the generator (beta = 0.5): construction customers pay ~8% later than their base
behaviour, real-estate customers ~30% later. Excluding the Covid years 2020–2021 from the average
changes the construction index only marginally (1.17), so the simple formula is kept and declared.

## 5. Phase 1C — The fictional company and the 8 scenarios

### The company

| Parameter | Value |
|---|---|
| Name | "DemoCo Building Supplies S.à r.l." (fictional, stored only in the vault) |
| Activity | Wholesale of building and installation materials, Luxembourg |
| Size | 90 employees, ~€24.9m revenue, 30% gross margin |
| Net profit on paper | €0.46–0.67m per year (2–2.7% of revenue) |
| Customers | 237 in 5 segments; top-20 ≈ 60% of revenue |
| Suppliers | 25; one major supplier ≈ 35% of purchases |
| Payment behaviour | 4 archetypes (punctual, normal, slow, chronic late) + sector stress + seasonality |
| As-of date | Monday 28 September 2026; 52 weeks of history; 13-week horizon to 27 December |
| As-of bank balance | €1.2m in every scenario |
| Safety threshold | 4 weeks of fixed cash costs ≈ €510k |
| Credit line | €1.0m, undrawn |

### The 8 scenarios — all acceptance checks pass

| ID | What is hidden in the data | Check (on the hidden future) |
|---|---|---|
| S1 Normal | Nothing | Balance stays above threshold for all 13 weeks |
| S2 Big customer | A top-3 customer slowly drifts from +10 to +45 days late; €1.4m inventory purchase from the major supplier in week 6 (later reduced to €950k net, €1.11m with VAT, and the drift extended to +60 days; see `ingestion/generator/scenarios.py`) | Balance falls below threshold in weeks 6–9, while the on-time projection would not |
| S3 Sector crisis | All construction customers except the top 5 pay 30–50 days later (scaled by the STATEC index 1.16); 2 small construction customers go bankrupt | Balance below threshold in weeks 7–11; no single customer explains > 20% of the gap |
| S4 Outflow spike | Extraordinary supplier bill (€1.1m) and a tax advance in the same week (week 7) | Below threshold in week 7, back above in week 8 |
| S5 Seasonality | August and December slowdowns visible in history | December receipts ≥ 15% below November |
| S6 New customer | New installer, 2 invoices (€150k), no payment history, truly "slow" | Pays ≥ 15 days late |
| S7 Partial payments | 3 customers pay 50–70% on time, the rest weeks later | Partial payments sum to the invoice |
| S8 Month-end close | Accountant closes each month 15–20 days late; September close cancels a €60k invoice and adds €25k credit notes | Booked revenue differs from invoiced by the adjustments |

### Review of the first generator run — problems found and fixed

| Problem | Fix |
|---|---|
| Net profit €2–3.5m (8–14%): unrealistic for a distributor | Full P&L reconciled (payroll, rent, opex, depreciation, tax): now €0.46–0.67m |
| Large supplier bill reduced profit | Treated as inventory purchase: cash out, profit unchanged |
| As-of balance from €0.40m (already below threshold) to €1.64m | Opening-balance solver fixed: €1.2m in every scenario |
| Top-20 share up to 65% | Now 59.8–60.3% everywhere |
| S3 could not produce a shortfall (25 customers too few; delays only shift cash) | Redesigned: whole construction cohort except top 5, scaled by the STATEC index, plus 2 bankruptcies |
| S4 spike in week 8 recovered by natural inflows | Moved to week 7 |

## 6. Data protection (summary of `docs/data_protection.md`)

- **Collected**: bank balances and transactions, invoices, payment dates, sector codes. No data about
  individuals.
- **Purpose**: cash forecasting and explaining shortfalls only.
- **Minimisation**: customers and suppliers as codes; names and IBANs only in the encrypted vault.
- **Security**: role separation, vault encryption, audit log, immutable parameters, secrets in `.env`.
- **Retention**: transactional data 24 months rolling; audit log 10 years (to confirm with legal).
- **LLM use** (from Phase 4): only aggregated, pseudonymised figures; with the local model nothing
  leaves the machine.
- **References**: GDPR, CNPD. **All data in the repository is synthetic.**
